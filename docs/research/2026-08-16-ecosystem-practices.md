## Proposed adoptions (ranked; each names its landing phase)

1. **Two-tier guard testing on the official testkit** (`@deepseek-ai/dsh-agent-loop-testkit`,
   proven in dsh-turn-budget): deterministic per-denial-code tests booting the
   REAL agent loop with a scripted adapter on every push, plus one subprocess
   smoke. Upgrades our custom e2e into ecosystem-standard CI. → P2 amendment
   to the P1-shipped testing story.
2. **3-strike escalation returns `ask`, not `deny`** (dsh-tool-policy pattern):
   the dsh approval seam then produces the immutable human-gate interaction —
   §8 "approvals are harness events" implemented for free. → P2.
3. **ProjectionDefinition discipline** (dsh-background-agents): stateVersion +
   zod wire schema + `ignorable: true` custom events + provenance-tagged
   migration + the crash/remount refold test copied verbatim as the P2 gate;
   one `vocabulary.ts` owning denial codes and fact shapes. → P2.
4. **Guards refuse to mount inert** (dsh-turn-budget): a guard whose config
   enables nothing is a boot FAILURE — profile boot becomes a truth test of
   invariant §10.3. → P2 (small; guards package).
5. **Distribution = npm bundle manifest** (`dsh.bundle.patch` → cordis.patch.yml
   row with safe defaults, bundle-contract vitest spec, `dsh plugin add`
   one-command install), plus **HARNESS_COMMIT pin file + scheduled
   re-attestation + pack-and-install smoke** (dsh-background-agents CI). → P3.
6. **`awt verify` ladder** (create-dsh-plugin): typecheck → build → offline
   smoke → `--dump-config` composition proof → scripted denial; always on
   scratch profiles, never the author's real thesis profile. → P2 scaffold.
7. **Enforcement-semantics README format**: four-column table (constraint |
   seam | what is counted | typed outcome) + a mandatory "what this does not
   do" section per guard (e.g. quote guard cannot stop edits made outside dsh
   tool calls). → P2 docs; also reshapes parent spec §7 table.
8. **pi-ai credential discipline**: `apiKeyEnv` references only, typed
   fail-loud `MISSING_CREDENTIAL` instead of ambient-key fallthrough. → P3
   profile config.

## Beat: The third-party dsh plugin ecosystem

**Scout verdict.** The third-party dsh plugin ecosystem is real, large (1,582 dsh-plugin topic repos per the audit; npm now carries registries like dsh-store claiming 550+ plugins, marketplaces, a static vetting tool, and a scaffolder), and has already converged on conventions AWT should adopt wholesale rather than invent. The canonical plugin shape: npm package with named exports name/inject/Config/apply, schemastery Config beside the TS interface, `dsh.bundle.patch` → cordis.patch.yml inserting a composition row with shipped defaults, rc-range-pinned peers, installed via `dsh plugin --profile X add <npm|github:#tag|path>`. Testing splits into a clear two-tier pattern the exemplars share: pure kernels unit-tested standalone, then integration tests that boot the REAL agent loop through the official @deepseek-ai/dsh-agent-loop-testkit with scripted LlmAdapters and assert on session-log events — deterministic, credential-free, and exactly what AWT P1's red-first denial tests need. Distribution truth-testing is also established: pack the tarball, install into a fresh DSH_HOME scratch profile through the official forwarder, assert `--dump-config` carries the row; dsh-background-agents runs this in CI against a HARNESS_COMMIT-pinned harness rebuild with a committed-lib build-drift gate — a complete working implementation of AWT §2.2's re-attested pinned baseline. Quality tiers were sharply distinguishable: turn-budget (#131-cited, fail-closed, honest limits) and background-agents (two releases, crash-recovery-tested stateVersion'd projections) are battle-tested exemplars; dsh-tool-policy is engineering-exemplary (pure policy kernel, argument-free reasons, bundle-contract tests, deny-by-default) but new; agent-teams is solid with the ecosystem's best plugin-development docs and verification pyramid; dsh-delegate merely exists. Two design validations for AWT worth flagging: (1) content-free typed denials and pure-evaluator/thin-listener guards are independently converged-upon practice, not AWT invention — §15 Q2 should resolve to TypeScript-native pure kernels, no Python shell-out; (2) the `ask` decision routed to dsh's own approval seam is the ready-made mechanism for §8's approvals-as-harness-events. Biggest gap AWT would NOT find a precedent for: nobody on the beat yet does file-path/content-aware write guards (notes-before-chapters, quote-span diffs) — dsh-tool-policy's name+argument matching is the nearest seam, so AWT's guards genuinely extend the ecosystem there. ### Practices

#### Testkit-booted real-agent-loop denial tests (no live model)

- **Source:** Nunchakus888/dsh-turn-budget — tests/turn-budget.spec.ts (clone: scratchpad/eco/dsh-turn-budget)
- **Pattern:** E2e guard tests boot the REAL dsh agent loop via the official published testkit (`mountAgentLoopTestDependencies` from @deepseek-ai/dsh-agent-loop-testkit), register the guard plugin plus a probe tool fixture, and drive turns with a ScriptedAdapter subclassing LlmAdapter that replays deterministic StreamChunk scripts (including scripted tool-call responses). Assertions read the session log, not internal state: turn/end reason `blocked`, tool/result blocks with isError and the denial text. Pure fold functions get a separate 'pure accounting' unit-test block.
- **Evidence:** `await mountAgentLoopTestDependencies(ctx); await ctx.plugin(AgentLoop, ...); await ctx.plugin(TurnBudget, config); ctx.llm.registerAdapter(['mock'], adapter)` then `expect(agent.session.events.findLast(e => e.type === 'turn/end')).toMatchObject({ data: { reason: { kind: 'blocked' } } })` and a filter for tool/result blocks where `block.isError && content.text.includes('turn budget exceeded')`. README: 'The integration tests boot the real Agent Loop with the published Harness testkit.'
- **AWT application:** P1 §7's 'CI proves every Enforced row with a red-first test' should be two-tier: this testkit tier as the per-denial-code deterministic gate (attempt chapter-write-without-notes / 16-page read / quote-span edit through a scripted turn, assert the exact typed code in session events — fast, no API key, runs on every push), plus one true `dsh --profile awt-headless` subprocess smoke. Without this pattern, P1's 'live headless run' gate needs credentials and is flaky; with it, every NOTES_MISSING/PAGE_RANGE_EXCEEDED/QUOTE_SPAN_MODIFIED/CONTRACT_SCOPE row gets a deterministic red-first test.

#### Pure policy kernel + thin hook listener, reasons never carry content

- **Source:** Drifter-yh/dsh-tool-policy — src/policy.ts and src/index.ts (clone: scratchpad/eco/dsh-tool-policy)
- **Pattern:** The guard is split into a Cordis-free pure module (compilePolicy validates and fails loud at load; evaluatePolicy is a pure function over (compiledPolicy, toolName, args) returning allow/ask/deny + reason) and an ~80-line plugin that just maps the evaluation onto the tools/pre-execute waterfall ({kind:'deny'|'ask', reason} or next()). Deny-by-default (`defaultDecision` defaults to 'deny'), first-match ordered rules, and reasons are constructed from rule metadata only — tool arguments are deliberately never interpolated. The 'ask' decision delegates escalation to dsh's own approval seam instead of reimplementing approval.
- **Evidence:** policy.ts header: 'The module has no Cordis dependency, so applications can validate policy behavior before mounting the plugin.' Rule doc: 'Human-readable reason for ask or deny; arguments are intentionally not interpolated.' evaluatePolicy doc: 'no arguments are copied into policy reasons.' index.ts: `ctx.on('tools/pre-execute', (exec, next) => { const evaluation = evaluatePolicy(policy, exec.name, exec.arguments); ... case 'ask': return Promise.resolve({ kind: 'ask', reason }) ...`
- **AWT application:** Answers open question §15 Q2: structure each AWT guard as a harness-neutral pure evaluator (notes-lint check, quote-span diff, contract-scope match, page-range parse) plus a thin dsh listener in the same TS package — no Python process boundary needed, and validators stay independently testable. It also makes §7's 'denials are typed and content-free … never prompt or manuscript text' true by construction. Additionally, guards that need a human verdict (3-strike ESCALATION_REQUIRED) should return `ask` so the immutable approval interaction is produced by dsh's approval seam — exactly the §8 'approvals are harness events' mechanism, for free.

#### Pinned-harness CI re-attestation + pack-and-install smoke + build-drift gate

- **Source:** PerryLink/dsh-background-agents — HARNESS_COMMIT, .github/workflows/ci.yml, scripts/pack-smoke.mjs (clone: scratchpad/eco/dsh-background-agents)
- **Pattern:** The repo pins its compatibility baseline in a plain HARNESS_COMMIT file. CI clones and builds that exact harness commit (cached by commit key), typechecks/tests the plugin against it, runs a build-drift gate (`pnpm run build && git diff --exit-code lib/` so committed lib/ enables github:#tag installs), then a pack smoke: pnpm pack → offline gate that every file the manifest promises exists and dsh.bundle.patch points at ./cordis.patch.yml → install the tarball into a fresh DSH_HOME profile via the official `dsh plugin --profile smoke add <tgz>` → assert `--dump-config` contains the plugin row and no FAILED. Tag-triggered npm publish is idempotent and skips gracefully without a token ('git install stays the primary channel').
- **Evidence:** ci.yml: 'Continuous integration: typecheck + tests against the pinned harness commit (HARNESS_COMMIT), the committed-lib build-drift gate, and the pack-and-install smoke.' pack-smoke.mjs: `runCli(harness, ['plugin', '--profile', 'smoke', 'add', tgz], { env: { ...process.env, DSH_HOME: home } })` then `if (!dump.includes('background-agents')) throw new Error(...)`. Publish step: 'The publish is idempotent: a version already on the registry … skips instead of failing.'
- **AWT application:** This is §2.2's 'pinned-commit compatibility baseline is re-attested before every release' turned into concrete files: AWT should carry a HARNESS_COMMIT (or pinned @deepseek-ai/dsh version) file, a scheduled workflow that rebuilds that commit and reruns the guard test suite against it, and a pack smoke that installs the awt-headless profile into a fresh DSH_HOME and asserts --dump-config carries every guard row. Add the pack smoke to P1's gate; adopt the idempotent tag-publish shape for distribution (§3.2 stays honest: publishing is proven, adoption is not claimed).

#### Versioned session-log projections with provenance-tagged migration and refold-after-crash tests

- **Source:** PerryLink/dsh-background-agents — src/projection.ts, src/vocabulary.ts, tests/integration.spec.ts (clone: scratchpad/eco/dsh-background-agents)
- **Pattern:** Governance state is a ProjectionDefinition folding the append-only session log: `stateVersion` bumps whenever fold semantics change so old persisted checkpoints refold instead of replaying into garbage; custom events are stamped `ignorable: true` so readers that don't know the type skip them; every durable fact also rides event types the harness already knows so state reconstructs from the log alone; a schema (zod) types the wire value. Migration between fact formats is handled by tagging each folded row with channel provenance ('legacy' | 'event') so logs carrying both channels never double-count. A dedicated vocabulary.ts owns the canonical serialized forms and parsers that return undefined for foreign producers. The proof is an integration test that flushes the log, disposes the context (simulated crash), remounts on the same persistence root, and asserts the projection value reconstructs from the durable log alone.
- **Evidence:** projection.ts: 'stateVersion bumps whenever the fold semantics or the serialized state fields change, so persisted checkpoint rows from an older unit refold instead of replaying into garbage' (`stateVersion: 2`), StateEntry has `readonly source: 'legacy' | 'event'` with the comment 'a log that carries both channels … never double-counts'. integration.spec.ts: 'recovers the child catalog and the projection facts after a parent-session reopen' — flush, `ctx.fiber.dispose()`, remount, `expect(projection?.agents.map(row => row.agentId)).toEqual([childId])`, and `expect(reopenedFacts.every(fact => fact.ignorable === true)).toBe(true)`.
- **AWT application:** This is §8's 'projections, not ledgers' fully realized: implement the page-budget counter, revision-attempt counter per contract, and integration-status lifecycle each as a ProjectionDefinition with stateVersion, a zod wire schema, `ignorable: true` on any custom guard-fact events, and a vocabulary.ts shared by guard, reducer, and tests (typed denial codes + fact shapes live there once, parsed defensively). Copy the crash/remount test verbatim as the P2 'refold tests green' gate; the provenance-tag pattern is the recipe for evolving reducers mid-thesis without corrupting old session checkpoints.

#### Load-time rejection of inert or invalid guard config

- **Source:** Nunchakus888/dsh-turn-budget — src/index.ts validateConfig (also Drifter-yh/dsh-tool-policy src/policy.ts compilePolicy)
- **Pattern:** The schemastery Config schema is exported beside the TS interface, and apply() additionally runs semantic validation that throws BEFORE any listener registers: non-positive/fractional limits are load errors, and a config that enables no ceiling at all is rejected outright — a mounted policy that would silently enforce nothing is a boot failure, not a quiet pass. The rejection is unit-tested ('rejects an inert or invalid policy at load time').
- **Evidence:** src/index.ts: '/** Require at least one active ceiling so a mounted policy cannot silently do nothing. */ export function validateConfig(config) { … throw new Error(`${name}: configure at least one turn budget`) }' called first in apply(); test: `expect(() => TurnBudget.validateConfig({})).toThrow('configure at least one')`.
- **AWT application:** Each AWT guard should refuse to mount inert: a page-budget guard with no limits configured, a notes guard with no notes-lint path, a contract-scope guard with no contract source must throw at profile boot rather than mount as a no-op. This is the plugin-level enforcement of invariant §10.3 / the 'no third state' rule — an Enforced row whose guard silently degraded to nothing is the exact failure mode this pattern makes impossible, and the awt-headless profile boot itself becomes a truth test of the enforcement claims.

#### npm bundle manifest convention (dsh.bundle.patch) with a bundle-contract test and shipped safe defaults

- **Source:** Drifter-yh/dsh-tool-policy — tests/bundle.manifest.spec.ts + cordis.patch.yml (convention also in dsh-turn-budget, dsh-background-agents, dsh-agent-teams package.json)
- **Pattern:** Distribution is one npm package: package.json declares `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`, the files whitelist ships the patch, and the patch inserts a composition row (id/name/config) carrying conservative defaults so `dsh plugin --profile X add <pkg|github:|path>` is the whole install. The exemplary extra: a vitest spec asserts the distribution contract itself — dsh.bundle.patch path, exports entry, files inclusion, patch file existence — and parses cordis.patch.yml with the official entryListSchema, asserting the exact default row (deny-by-default ships as the default config). Peer deps are pinned to the real rc range (`>=0.1.0-rc.6 <0.2.0`), not `*`.
- **Evidence:** bundle.manifest.spec.ts: `expect(packageManifest.dsh?.bundle?.patch).toBe('./cordis.patch.yml')` … `expect(parsed).toEqual([{ insert: [{ id: 'tool-policy', name: 'dsh-tool-policy', config: { defaultDecision: 'deny', rules: [] } }] }])`. dsh-turn-budget package.json: `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`, `"files": ["dist", "cordis.patch.yml", …]`, peerDependencies `"@deepseek-ai/dsh-tools": ">=0.1.0-rc.6 <0.2.0"`.
- **AWT application:** AWT's guards package and profiles (§5) should ship exactly this shape — cordis.patch.yml rows with enforcement defaults ON — and add a bundle-contract spec per package so the distribution claim is itself a tested claim (docs-are-executable-claims applied to install instructions). Pin peer ranges to the attested rc line; the audit shows npm latest/next divergence (`0.0.1-rc.1` vs `0.1.0-rc.6`) is a real trap the whole ecosystem defends against.

#### Scaffold-embedded verification ladder ending at --dump-config composition proof

- **Source:** create-dsh-plugin (npm tarball: scratchpad/eco/npmpkgs/create-dsh-plugin-0.1.1) src/verify.js + NanmiCoder/dsh-agent-teams docs/verification-guide.md
- **Pattern:** The ecosystem's standard verification pyramid: typecheck → build → offline pure-logic smoke (temp dirs, self-cleaning) → `dsh --profile <scratch> --dump-config` (proves the plugin row composes into the config tree offline, no boot, no API key) → real headless task → GUI probe; all on isolated profiles/ports, never a running instance. create-dsh-plugin bakes the first four levels into the scaffold as `--verify`: install → tsc build → `dsh plugin add` into a temp DSH_HOME profile → dump-config grep for the plugin row, explicitly noting it 'proves compile + load + config composition' without credentials. Templates additionally pin the correct dist-tag at generation time and embed the known pitfalls as comments in generated code.
- **Evidence:** verify.js: `run('npx', ['-y', '@deepseek-ai/dsh', 'plugin', '--profile', profile, 'add', targetAbs], { env: { ...env, DSH_HOME: dshHome } })` then `r.stdout.includes(cfg.pluginId)` on `--dump-config`; README: 'Without a DEEPSEEK_API_KEY it proves compile + load + config composition.' verification-guide.md: four-layer pyramid with layer 2 = 'dsh --profile <scratch> --dump-config 验证 bundle 补丁能组合进配置树（不 boot、不碰实例）'.
- **AWT application:** Give `awt init` a sibling `awt verify` implementing this ladder for the generated workspace: profile composes (--dump-config contains every guard row), notes lint runs, one scripted-adapter denial fires. Use the dump-config tier as P1's cheap always-on CI gate below the testkit tier, and copy the pitfall-comments-in-generated-code idea into the scaffold's workspace config. Also adopt the hard rule that all verification runs on scratch profiles/temp DSH_HOME — never the author's real thesis profile.

#### Enforcement-semantics tables and stated-against-interest non-claims in plugin READMEs

- **Source:** Nunchakus888/dsh-turn-budget README.md ('Enforcement semantics' table) + Drifter-yh/dsh-tool-policy README.md ('Security model' / 'What this does not do')
- **Pattern:** The battle-tested plugins document enforcement as a four-column table (limit | enforcement point | counted work | outcome) and dedicate explicit sections to what the plugin does NOT do, including honest boundary conditions of their own enforcement ('a provider can exceed the configured ceiling inside its current response'; 'a deny rule makes the matched call unavailable, not destructive behavior impossible in general'), positioning against adjacent layers as complementary rather than superior. The turn-budget author restated these limits in official Discussion #131 against interest — which is precisely why the audit ranks it the credible precedent.
- **Evidence:** turn-budget README: 'This is a circuit breaker, not a billing system. It does not estimate currency, rewrite tool arguments, replace sandboxing or approvals, or terminate an uncooperative model/tool operation in the middle of a step.' plus the Limit/Enforcement point/Counted work/Outcome table. tool-policy README: 'Community plugin. Not affiliated with or maintained by DeepSeek AI.' and 'dsh-tool-policy does not implement sandboxing, capability enforcement, shell semantic analysis, or equivalent-operation detection.'
- **AWT application:** Rewrite §7's Enforced table in the four-column enforcement-semantics format (constraint | hook seam | what is counted/diffed | exact outcome + typed code), and require every guard's README to carry a 'what this does not do' section — e.g., the quote-integrity guard cannot stop edits made outside dsh tool calls; the page-budget guard counts read events, not model memory. This operationalizes the spec's own rule that no advisory behavior may wear enforcement vocabulary, in the format the ecosystem's most credible plugin already proved out.

## Beat: The pi-ai provider ecosystem

**Scout verdict.** The pi-ai ecosystem is the strongest external validation yet for AWT's §9.1 provider-neutrality plan, and it is battle-tested rather than aspirational: pi-ai is Mario Zechner's (badlogic) production library behind the pi coding agent, with issue-annotated retry classifiers, 59 issue-numbered offline regressions, and a no-real-keys test policy written into AGENTS.md. Three findings matter most for the AWT rebuild. (1) Provider neutrality is achieved by layering: a small set of wire-protocol 'api' implementations reused by 30+ provider definitions (deepseek.ts is 15 lines: id + baseUrl + envApiKeyAuth + openAICompletionsApi), and dsh's llm-pi-ai adapter then makes everything above that pure configuration — AWT profiles therefore only need to write the llm-pi-ai providers section (apiKeyEnv references, narrowed model lists, per-route retryPolicy) and hardcode nothing; the adapter's fail-loud semantics (MISSING_CREDENTIAL, UNKNOWN_MODEL pre-network, refuse-don't-skip overrides, reject-where-written config) are exactly the typed-denial discipline §7 wants and should be mirrored in AWT's own profile validation. (2) The scripted-provider testing story AWT's e2e plan needs already exists at two levels — pi's in-library faux provider driving the full app stack, and dsh's scripted mock HTTP server plus key-gated real-API lane — and both map cleanly onto AWT's E0/E1 evidence classes; the faux-provider harness is the direct template for the P1 red-first guard tests. (3) Counting integrity: dsh forces SDK retries to zero so exactly one layer owns retry — a prerequisite AWT's session-log projections silently depend on (attempt counts lie if two layers retry), worth stating as an explicit P2 invariant. Also worth borrowing: pi's manifest-hashed offline model-data pinning for the §2.2 re-attestation workflow, and dsh's immutable per-operation config snapshots for guard determinism. pi-telemetry's adapter-conformance-test pattern (reference in-memory impl + conformance suite any adapter must pass) is a lighter-weight bonus idea for keeping AWT's scripted e2e adapter honest against the real route. Other org repos (pi-chat, pi-share-hf, gondolin) exist but add nothing AWT needs beyond the monorepo. Sources: cloned repos at .../scratchpad/eco/pi (commit 086c32e7, 2026-08-15) and .../scratchpad/eco/dsh; npm view @earendil-works/pi-ai@0.84.2; web: https://github.com/earendil-works, https://github.com/earendil-works/pi, https://github.com/earendil-works/pi-chat.

### Practices

#### Credential references (apiKeyEnv), never secrets, with typed fail-loud resolution

- **Source:** deepseek-harness clone: packages/llm/llm-pi-ai/README.md (Config section) + pi clone: packages/coding-agent/src/core/resolve-config-value.ts
- **Pattern:** Provider config carries a credential *reference* ($ENV_VAR, ${ENV}, or !shell-command), resolved per request, never an inline secret. Two hard rules: (1) a configured reference that resolves to nothing fails the request with a typed error instead of falling through to ambient env discovery ('falling through would authenticate with whatever unrelated key the environment happens to hold'); (2) introspection APIs (getConfigValueEnvVarNames, isConfigValueConfigured, getMissingConfigValueEnvVarNames) let surfaces report configured/missing WITHOUT resolving the secret. Resolved values are trimmed and format-checked before use so a bad key fails as INVALID_CREDENTIAL naming the route and reference — 'but never any part of the key' — instead of an opaque fetch TypeError.
- **Evidence:** dsh llm-pi-ai README: 'apiKeyEnv is a credential reference resolved per request, so no secret enters this file… a configured reference that resolves to nothing fails the request with MISSING_CREDENTIAL'. pi resolve-config-value.ts implements $VAR/${VAR}/!command parsing, resolveConfigValueOrThrow naming the missing env vars, and enumeration-without-resolution helpers. pi-ai's CredentialStore contract additionally states 'Enumeration must not resolve secrets or execute configured key commands' (packages/ai/README.md, Credential Store).
- **AWT application:** P1 profiles (spec §9.1): awt-web/awt-headless profile YAML should configure llm-pi-ai routes with apiKeyEnv references only; the profile validator answers 'is this route configured' without touching secrets; a P1 red-first CI test asserts the typed MISSING_CREDENTIAL when the referenced var is unset, matching §7's typed-denial discipline.

#### Scripted in-library faux provider as the app-level e2e harness

- **Source:** pi clone: packages/ai/src/providers/faux.ts (708 lines) + packages/coding-agent/test/suite/harness.ts + AGENTS.md
- **Pattern:** The LLM library itself ships an in-memory 'faux' provider (registerFauxProvider) that the full application stack runs against: tests call setResponses([...]) with either static assistant messages or context-inspecting factories (FauxResponseFactory receives context, options, call-count state, model), including scripted tool calls (fauxToolCall), thinking blocks, error stopReasons, and aborts. The test harness wraps the real session/settings/auth managers around it and exposes typed event capture (eventsOfType). A project rule makes it mandatory: no real provider APIs or keys in the suite.
- **Evidence:** harness.ts: 'const fauxProvider = registerFauxProvider({models: options.models}); fauxProvider.setResponses([])' driving the real AgentSession + SessionManager + SettingsManager; faux.ts fauxAssistantMessage supports stopReason and errorMessage options for failure scripting. AGENTS.md: 'For packages/coding-agent/test/suite/, use test/suite/harness.ts + the faux provider. No real provider APIs, keys, or paid tokens.'
- **AWT application:** Directly the model for AWT's scripted-adapter e2e (§7 CI red-first tests, P1 gate): drive the live awt-headless profile with a scripted adapter whose factory deterministically emits the forbidden tool call (chapter write without notes, 16-page read, quote-span edit) and assert the exact typed denial (NOTES_MISSING, PAGE_RANGE_EXCEEDED, QUOTE_SPAN_MODIFIED); error/abort scripting exercises the 3-strike fold.

#### Issue-numbered offline regression suite

#### Single retry authority: SDK/provider retries forced to zero, one agent-level policy, errors-as-data

- **Source:** deepseek-harness clone: packages/llm/llm-pi-ai/README.md + pi clone: packages/ai/src/utils/retry.ts + packages/coding-agent/docs/settings.md
- **Pattern:** Exactly one layer owns retry. The dsh adapter pins pi-ai's SDK maxRetries to 0 so 'one stream() call makes one provider request', and the removed profile fields fail load instead of silently multiplying the separately composed agent-level budget. The agent-level policy is bounded exponential backoff over errors that flow as data (AssistantMessage stopReason 'error'), with a classifier that checks NON-retryable patterns (quota/billing/subscription limits) before retryable ones so deterministic failures fail fast; aborts are terminal, and aborts during backoff sleep are normalized to the same aborted-message shape.
- **Evidence:** dsh README: 'The adapter forces pi-ai's SDK maxRetries to zero so one stream() call makes one provider request. The removed profile fields maxRetries and maxRetryDelayMs fail load instead of silently multiplying…'. pi settings.md: 'Keep retry.provider.maxRetries at 0 unless provider-level retries are explicitly needed… can make SDK/provider retries handle out-of-usage-limit errors before Pi sees them.' retry.ts: NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN tested first in isRetryableAssistantError; delay = baseDelayMs * 2^(attempt-1).
- **AWT application:** AWT's session-log projections (§8) count attempts: if two layers retry, folded counts lie. Profiles must pin the llm-pi-ai per-route retryPolicy and treat dsh's agent-level policy as the sole retry authority so the 3-strike escalation fold and page-budget counters stay truthful; the refold test should include a scripted transient-error run proving one attempt event per logical attempt.

#### Generated, manifest-hashed model catalog with offline pinning

- **Source:** pi clone: packages/ai/scripts/model-data.ts, generate-models.ts, check-model-data.ts + root README ('Building standalone binaries')
- **Pattern:** Live provider catalogs are baked into committed generated snapshots (per-provider *.models.ts) plus a .manifest.json carrying schemaVersion, generatedAt, structureHash, and per-file SHA-256 hashes. A standalone validator distinguishes missing vs stale data and prints the exact remediation command; release builds take --offline-model-data to build from the committed snapshot instead of refreshing from the network, and the snapshot ships inside the release source archive so third parties reproduce the exact catalog. Humans never edit the generated file (written rule), only the generator.
- **Evidence:** model-data.ts: MODEL_DATA_SCHEMA_VERSION = 3, ModelDataManifest {schemaVersion, generatedAt, structureHash, files}; check-model-data.ts: 'Model data is missing or stale. Run npm run hydrate:model-data'; README: '--offline-model-data builds with that snapshot instead of refreshing it from live provider catalogs'; AGENTS.md: 'Never modify packages/ai/src/models.generated.ts directly'.
- **AWT application:** Extend §2.2's pinned-commit baseline: the scheduled re-attestation workflow should also pin a hashed model-catalog snapshot (which models/context windows the profiles resolved against), so E1 paired-session results (§11) are reproducible against a byte-identified catalog, not whatever pi-ai's catalog says on rerun. Same manifest+refold discipline AWT already applies to reducers (stateVersion).

#### Catalog-route inheritance with refuse-don't-skip overrides and pre-network typed failures

- **Source:** deepseek-harness clone: packages/llm/llm-pi-ai/README.md (Config + Catalog resolution sections)
- **Pattern:** A route naming an installed catalog provider inherits endpoint, wire protocol, and models as defaults and overrides field by field; a 'models' list REPLACES the catalog (narrowing is explicit), while modelOverrides reshapes single models in place. Misdirected config is refused rather than skipped: an override naming a model the catalog doesn't describe fails load 'because a silently unchanged model is a typo someone would otherwise hunt for'; an unconfigured model id fails before any network I/O with typed UNKNOWN_MODEL; an unsupported reasoning effort fails the request with UNSUPPORTED_REASONING_EFFORT 'before network I/O instead of being clamped'. Unserviceable profiles are rejected where they are written (settings-rejected naming route and model), and the settings seam keeps the last good value.
- **Evidence:** README: 'Model ids are not lifecycle config; a model the route does not configure fails before any provider request with LlmError(UNKNOWN_MODEL)'; 'Overrides… naming a model the catalog does not describe is refused rather than skipped'; 'an unserviceable profile is refused where it is written… rather than being stored and then quietly disabling every route'. Backed by 971 lines of catalog.spec.ts.
- **AWT application:** The concrete shape of §9.1 provider elasticity: awt profiles narrow each route to the exact models the thesis workflow uses (one prose-fidelity route, one cost route), with unknown-model and unsupported-option failing typed and pre-network — the same 'refuse, don't skip; fail where written' rule AWT should apply to its own profile/guard config validation in P1.

#### Immutable per-operation configuration snapshot with atomic re-registration

- **Source:** deepseek-harness clone: packages/llm/llm-pi-ai/README.md (Provider/model routing section) + tests/dynamic-config.spec.ts
- **Pattern:** Every operation captures a whole immutable snapshot (profiles + constructed provider collection) before its first await; a configuration change builds a NEW collection rather than mutating the in-use one, because lazy resolution would otherwise let a request start under one configuration and finish under another. Route re-registration is atomic with the candidate set validated first — a collision leaves the previous routes serving — so 'switching models mid-reply takes effect on the next step, never inside the one in flight'.
- **Evidence:** README: 'Each resolution produces one immutable snapshot… every operation captures a whole snapshot before its first await. A configuration change builds a new collection rather than mutating the one in use… This is what makes the seam's per-step call freeze (llm.prepareCall()) hold end to end.' dynamic-config.spec.ts (217 lines) exercises live reconfiguration.
- **AWT application:** Apply to guards and reducers (§7/§8): a guard evaluating a tool call should capture the active edit-contract and budget state as a snapshot per evaluation, and contract/config changes take effect at the next step — otherwise mid-turn changes make denials and the 3-strike fold non-deterministic and the refold test unprovable.

#### Two-tier test lanes: scripted wire-level mock server by default, key-gated real-API e2e as a separate lane

- **Source:** deepseek-harness clone: packages/llm/llm-pi-ai/tests/mock-server.ts + adapter.e2e.ts; pi clone: root README/test.sh
- **Pattern:** Adapter correctness is proven offline against a local scripted HTTP server that replays per-request behaviors (status, SSE event scripts, delays, headers) and records paths/bodies/headers for assertion — 'script exhausted' fails loudly. Real-provider e2e is a separate, explicitly key-gated lane (skipped without env keys) that mirrors the same output contract via a shared assemble helper, so the two lanes assert the same shape. Test volume follows: 4,243 lines of tests over 2,706 lines of source in the dsh adapter.
- **Evidence:** mock-server.ts: 'Local provider stand-in: replays scripted behaviors per request', textEvents array of chat-completions SSE lines, fallback '{status: 500, body: script exhausted}'. adapter.e2e.ts header: 'Real-API e2e… Key-gated.' pi README: './test.sh — Run tests (skips LLM-dependent tests without API keys)'.
- **AWT application:** Maps onto AWT's evidence classes (§11): E0 = the offline scripted lane (guards + adapter contract, runs in every CI), E1 = the key-gated real-route lane (paired-session instrument), never conflated. ### Practices

#### Real-entry-path e2e: boot the shipped composition, never hand-mount the plugin

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — docs/postmortem/0001-acp-default-export-drops-inject.md, docs/testing.md, examples/AGENTS.md
- **Pattern:** Every product-visible plugin gets at least one keyless test that loads it through the real Loader/export path (subprocess, real cordis.yml, published bin), because hand-built `ctx.plugin({name, inject, apply})` mounts bypass export unwrapping and fiber topology entirely. Every example ships a keyless + with-key smoke pair; guards are proven by restoring the regression and watching the test go red. Plugins use namespace exports only — `export default` makes the Loader discard `inject`/`name`/`Config`.
- **Evidence:** PM 0001: 178 green unit tests and 100% coverage while the ACP server 'crashed the instant a real editor (Zed) connected', root cause a stray `export default apply` that `unwrapExports` resolved to a bare function; lesson: 'A test that constructs a plugin by hand cannot validate how the plugin loads.' Guardrail: no-key session/new e2e 'Verified it fails when export default apply is restored.' testing.md: 'A guard only guards if the regression actually fails it… introduce the regression, watch red, revert.'
- **AWT application:** P1's red-first CI rule (§7) should be stated as: each Enforced row's test boots the real awt-headless profile through the Loader/published entry as a subprocess, attempts the forbidden op, asserts the exact typed denial, then temporarily disables the guard row and asserts the test goes red. Also a hard authoring rule for AWT guard plugins: namespace exports (name/inject/apply), never export default; opportunistic services read via ctx.get(), not property access.

#### Guard authority ladder: waterfall policy vs deny-only terminal guards, no input rewrite

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — .agents/notes/implemented/feature/2026-06-30-interception-extension-points.md, docs/cookbook/extension-cookbook.md
- **Pattern:** Each interception phase gets exactly one kind of authority: `tools/pre-execute` is the reorderable typed-decision waterfall (allow/deny/ask); `ctx.tools.guard()` installs synchronous scope-aware invariants after the whole waterfall that 'may deny or abstain, never force-allow, so listener ordering cannot resurrect an operation that a final invariant forbids'; `tools/post-execute` transforms results; `tools/result` only observes. PreToolDecision deliberately cannot rewrite arguments (history/audit/UI are logged before execution), and `agent/session-start` is a pure notification that cannot block startup.
- **Evidence:** Note text: '`ctx.tools.guard()` installs synchronous scope-aware policy after the whole pre-execute waterfall. A guard may deny or abstain, never force-allow…'; 'PreToolDecision cannot rewrite arguments. History and the audit call are logged before execution… so the registry seals arguments before policy.'; 'agent/session-start… A pure notification — it CANNOT block startup.' Cookbook shows the canonical permission-gate plugin returning `{ kind: 'deny', reason: … }` from tools/pre-execute.
- **AWT application:** Refine §7's mechanism column: quote-integrity and notes-before-chapters are hard invariants → implement as ctx.tools.guard() (deny-only, immune to listener order), while edit-contract scope and ask-flows sit at tools/pre-execute typed decisions. Two spec consequences: (a) guards deny with a typed code, never 'fix' the write — argument rewrite is architecturally unavailable; (b) nothing can gate at session start, so all AWT enforcement must live at pre-step/pre-execute as §7 already assumes — worth stating explicitly.

#### Product-bin acceptance harness: scripted mock LLM + throwaway DSH_HOME profile fixture

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — apps/cli/tests/built-bin.e2e.ts, examples/headless-agent/tests/fixtures/cli-mock-llm.ts, packages/test-support/ (llm-mock-server, loader-smoke, agent-loop-testkit)
- **Pattern:** CLI acceptance runs the built bin (`apps/cli/lib/bin.js`) under plain node against `startMockLlmServer` from @deepseek-ai/dsh-llm-mock-server, with a custom profile synthesized into a mkdtemp DSH_HOME (a lifecycle-marker bundle: generated plugin.mjs + cordis.patch.yml listed in dsh.profile.bundles) — proving out-of-tree profile composition without booting the product tree. Deterministic agent behavior comes from a scripted LlmAdapter that emits a fixed tool-call → reads the tool result → emits the final answer, driving real tools keylessly.
- **Evidence:** built-bin.e2e.ts imports `startMockLlmServer` and builds 'A minimal custom profile: one lifecycle-marker plugin bundle listed in dsh.profile.bundles, no dsh-base — proving out-of-box composition machinery without booting the entire product tree' by writing plugin.mjs + cordis.patch.yml into mkdtempSync DSH_HOME. cli-mock-llm.ts scripts `stream()`: if no tool-result in messages, yield a bash tool-call ('printf CLI_TOOL_ROUND_TRIP'); else yield the final text — one real tool round trip, zero keys.
- **AWT application:** This is AWT P1's test harness, ready-made: synthesize awt-headless into a temp DSH_HOME, script the mock adapter to emit the forbidden call (write to chapters/** without notes, pages:1-20 read, quote-span edit), run `dsh --profile awt-headless` as subprocess, assert the exact typed denial (NOTES_MISSING, PAGE_RANGE_EXCEEDED, QUOTE_SPAN_MODIFIED) in the session log and the exit code. Reuse dsh-llm-mock-server and dsh-loader-smoke instead of building a driver.

#### Headless one-shot completion contract: durable flush before exit, exit code = turn/end reason

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — .agents/notes/implemented/architecture/2026-08-09-headless-direct-core-entry-point.md, examples/headless-agent/README.md
- **Pattern:** The headless runner's contract is precise: no listening port, no Host/Web packages in the tree (verified by a config-dump acceptance test), final assistant text + newline on stdout, empty stderr on success, exit 0 exactly when the durable turn/end reason is `completed`, terminal model errors written as durable code+message to stderr — and completion is derived only after `ctx.sessions.flush` so stdout and exit code never observe incomplete persisted state.
- **Evidence:** Note: 'It awaits ctx.sessions.flush, folds its durable event interval for the last non-empty assistant text and final turn/end reason, writes the text plus one newline to stdout, and requests bounded launcher shutdown with exit 0 exactly when the reason is completed.' Verification section: 'Config-dump acceptance excludes every Host, Web, and Client package from the shipped headless tree.'
- **AWT application:** Adopt verbatim as the awt-headless summon contract in §5's table (Claude Code/Codex/CI call `dsh --profile awt-headless "task"`): exit-code semantics keyed to the durable turn/end reason, flush-before-exit so the session log AWT's projections fold is complete when the caller sees exit, and copy the profile-purity config-dump test (awt-headless contains no web packages).

#### Session-log versioning: one integer, writer decides bumps, unknown events refuse loudly, never rewrite on view

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — .agents/notes/implemented/architecture/2026-08-10-session-log-version-mechanism.md
- **Pattern:** One monotonic version integer (no major/minor — convertibility is a property of each step's upgrader); the writer bumps whenever an old reader could no longer read with full semantic correctness ('parses without error is not the bar'); readers refuse newer versions direction-aware and convert older ones in memory, persisting the conversion only when the session is actually continued; unknown event types default to *required* (refuse) unless marked `ignorable: true` — 'forgetting the marker over-refuses a resumable session (an inconvenience), while a default of ignorable would make the same mistake silently resume a gutted one (a safety failure).'
- **Evidence:** Note: 'Silently skipping content that shapes reconstruction is a wrong read'; 'When unsure, bump: a near-identity upgrader is almost free, a missed bump silently corrupts old readers'; alternatives reject 'Auto-migrating on view — rewriting the artifact on open turns a read into a destructive write.'
- **AWT application:** Directly hardens §8/§10.4's stateVersion + refold design: make AWT reducers (page budget, revision attempts, integration status) fail loudly on unrecognized event types instead of skipping them — a skipped read event silently under-counts a page budget, the exact safety inversion this note names. Adopt writer-decides-bump for reducer schema, refold old checkpoints in memory, and never rewrite the persisted log as part of a fold.

#### Fail-closed approval seam with durable model-invisible audit pairs and one-shot grants only

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — .agents/notes/implemented/feature/2026-07-06-approval-seam.md
- **Pattern:** Approvals are a mechanism/policy split: `ctx.approval` owns dispatch + audit; answerers are waterfall listeners registered by the channel that owns the agent. Zero answerers → `unavailable` → deny ('fail-closed is the zero-listener default, not a configuration'); rejected/cancelled/unavailable are distinct typed reasons the model can tell apart; every resolved ask commits a durable `approval/asked`/`approval/decided` pair the model never sees; `allowed-once` authorizes exactly one call and nothing persists ('Advertising an option the harness cannot honor manufactures doomed grants' — allow_always deliberately unshipped); subagents are pinned to policy `never`.
- **Evidence:** Note: 'What happens in a deployment with no answerer at all (headless, CI)? Every ask falls through the empty waterfall to unavailable and the tool call denies'; 'approval/asked and approval/decided are durable log-only events; the model sees only the ordinary tool result'; 'allowed-once… nothing about a grant persists past the call that asked.'
- **AWT application:** AWT §8 'approvals are harness events' should reuse dsh-user-approval rather than invent events: author decisions (integration plan, escalation) ride ask → approval/asked/decided in the append-only log — exactly the artifact P2's re-run self-approval attack must show is model-unwritable. Set policy `never` for CI/headless E1 runs so unattended sessions deterministically auto-reject; keep AWT approvals one-shot (no standing grants), matching the note's deferred-allow_always reasoning.

#### Profiles/bundles as the distribution unit — with whole-row patch replacement and config-only !!js interpolation as known traps

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — .agents/notes/implemented/architecture/2026-08-05-profile-plugin-bundles.md, packages/bundle/base/README.md, docs/postmortem/0002-js-expression-disabled-filesystem-tools.md
- **Pattern:** A profile is $DSH_HOME/profiles/<name> with package.json carrying `dsh.profile.bundles` (explicit ordered layer list) plus a user cordis.patch.yml; a bundle is an npm package declaring `dsh.bundle.patch`. Two documented sharp edges: 'A patch replaces whole row configs — profile overrides must restate every field a row keeps; there is no deep-merge layer' (dsh-base README, Known Limitations), and `!!js` expressions evaluate only under plugin `config` — a `disabled: !!js …` on entry metadata is a permanently-truthy object (PM 0002), so conditional composition uses explicit overlay yml files, guarded by a `verify-cordis-config` static lint that rejects expression nodes in entry metadata.
- **Evidence:** PM 0002: 'Cordis evaluates JavaScript expressions only inside plugin config. The raw expression object was truthy, so the filesystem stack was always disabled. Snapshot refresh then accepted UNKNOWN_TOOL results as new expected outputs.' Guardrails: fs.cordis.yml overlay + 'dsh-acp-snapshot rejects structured UNKNOWN_TOOL results in fresh runs and committed session fixtures.'
- **AWT application:** Shapes §5 concretely: ship guards as dsh.bundle npm packages and awt-web/awt-headless as profiles listing [dsh-base, (dsh-web-app|dsh-headless), awt-guards] in explicit order; every AWT patch override restates the full row config; no conditional entry metadata — use overlay patch files; add a verify-cordis-config-style lint plus a snapshot semantic guard that rejects UNKNOWN_TOOL/absent-guard transcripts so a broken AWT composition can never be committed as an expected output.

#### Preserve structured failures across seams; classify outcomes by conjunction of independent evidence

- **Source:** deepseek-ai/deepseek-harness @ 47f9438 — docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md, docs/defensive-patterns.md
- **Pattern:** An adapter must surface the structured error owned by the seam below it, never replace it with its own nearest generic category (search wrapped SANDBOX_UNAVAILABLE as generic SEARCH_FAILED); process-outcome classification needs status-gated conjunctions (exit code AND exact fatal line), with informational exclusions exact and narrow and unknown fatal lines fail-closed; report orthogonal facts (timedOut, signal, exitCode) independently since 'a process can time out AND exit 0 because it trapped the signal.'
- **Evidence:** PM 0004 lessons: 'Process attribution requires a conjunction of independent evidence; a shared prefix is not a protocol' and 'An adapter must preserve structured failures owned by the seam below it instead of replacing them with its own nearest generic category' — a single `landlock-run:` substring rule made ripgrep's no-match exit 1 surface as SANDBOX_UNAVAILABLE. defensive-patterns.md: 'Surface each independent fact (timedOut, signal, exitCode) on its own.'
- **AWT application:** Decides §15 open question 2 safely: if AWT's TypeScript hooks shell out to the harness-neutral Python validators, the wrapper must propagate the validator's typed code (NOTES_MISSING etc.) verbatim, classify runs by exit-code + machine-readable output conjunction (e.g. JSON on stdout, never stderr substring matching), report timeout/signal/exit orthogonally, and treat any unrecognized validator outcome as a fail-closed denial — otherwise a validator crash silently degrades an Enforced row to advisory.

## Beat: App/distribution shapes on harness architectures

**Scout verdict.** The dsh app/distribution ecosystem is real but extremely young — @deepseek-ai/dsh has exactly six rc releases on npm (latest = next = 0.1.0-rc.6), the dsh-plugin GitHub topic exploded from 431 to ~3,000 repos in two days (mostly spam per dshworks' measured sweep), and nothing is battle-tested in the calendar sense. So I ranked by verifiable engineering rigor in files I read, not by adoption claims. The good news for AWT: the distribution grammar the design doc assumes is confirmed and settled. An app IS a profile — a directory with package.json (`dsh.profile.bundles`) + cordis.patch.yml — and installation IS package management: `dsh plugin --profile <name> add <npm|github:ref#tag|tgz-URL>` forwards to pnpm (deepseek-harness/apps/cli/README.md, read in clone). Community distributions (dsh-tui, black-whale, the desktop shells) all converge on the same five moves, which map cleanly onto AWT P1-P3: (1) pinned one-line install + dump-config verification probe + stated validated baseline; (2) engines.dsh + peer pins to the tested rc so incompatibility fails at install time; (3) committed build artifacts with a CI drift check so git installs need no toolchain; (4) scaffold/install steps that prove themselves against a throwaway DSH_HOME profile; (5) dated, machine-readable compat claims (verifiedAgainst/lastVerified) re-checked on a schedule with evidence-only reports. The breaking-change problem has three observed answers on a spectrum — caret-pin the rc line (plugins), exact-pin + version-keyed patches (dsh-desktop), vendor the whole deploy closure + lockstep tags (tauri desktop) — and the `.dsh-plugin` mechanism deletion (introduced ~08-09, removed 08-11, no migration) is the concrete case study proving §2.2's paranoia is warranted. Notable gap: the most AWT-shaped verticals (dsh-edu with its edush installer, dsh-cyber-sec's guard+evidence-domain profile, oh-my-dsh-distribution's pure-data recipes) sit in the private dsh-external org and could not be verified; the dsh-market app (900+ plugin marketplace) also exists but was not audited. ### Practices

#### Pinned one-line install with a documented post-install verification probe

- **Source:** 147228/dsh-black-whale — README.md 'Install' section (clone: /tmp/claude-0/-home-user-academic-writing-toolkit/daf361f6-42d0-5c0a-85a5-4f79cc265de5/scratchpad/eco/dsh-black-whale/README.md)
- **Pattern:** Distribute the app as a profile bundle installed by one command against a pinned artifact — `dsh plugin --profile web add <GitHub-Release .tgz URL>` (recommended) or `github:owner/repo#vX.Y.Z` — then document a deterministic verification probe (`dsh web --dump-config | grep <plugin-id>`), an upgrade command (re-add the new pinned tag), and an uninstall command. State the exact validated baseline in the README: harness version + Node version the release was acceptance-tested on.
- **Evidence:** README install block: `dsh plugin --profile web add https://github.com/147228/dsh-black-whale/releases/download/v0.1.3/xiaoyao-ai-dsh-client-ui-skin-black-whale-0.1.3.tgz`; alternative `dsh plugin --profile web add github:147228/dsh-black-whale#v0.1.3`; verification `dsh web --dump-config | grep -n "ui-skin-black-whale"`; baseline claim '当前版本在 DSH 0.1.0-rc.6、Node.js 24 上完成真实验收'. release.yml packs with `pnpm pack` and attaches the tgz via `gh release create --verify-tag`.
- **AWT application:** P3 distribution: publish AWT as release-tagged bundle tarballs; the README install section becomes exactly this quartet (pinned add / dump-config probe for `awt-guards` rows / pinned upgrade / remove), and every release states 'validated against dsh <ver>, Node <ver>' — the §2.2 pinned baseline made user-facing.

#### Harness compatibility declared in the manifest: engines.dsh plus peerDependencies pinned to the tested rc line

- **Source:** bugmaker2/dsh-plugin-template package.json; dsh-tui/dsh-tui package.json (clones under .../scratchpad/eco/dsh-plugin-template/ and .../eco/dsh-tui/)
- **Pattern:** The plugin package.json carries `engines: { "dsh": ">=0.1.0-rc.6" }` and caret-pinned peerDependencies on every consumed harness package (`"@deepseek-ai/dsh-agent": "^0.1.0-rc.6"`), with `peerDependenciesMeta.optional` for optional seams — so installing into an incompatible harness fails at `dsh plugin add` time, not at boot. Pair with an honest README compat posture ('under active development against the pre-release rc line; expect breakage until upstream stabilizes; peer dependencies pin the tested rc').
- **Evidence:** dsh-plugin-template/package.json: `"engines": { "node": "^22.19 || >=24", "dsh": ">=0.1.0-rc.6" }` + `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`. dsh-tui/package.json: peerDependencies block of `^0.1.0-rc.6` pins across dsh-agent/dsh-agent-loop/dsh-cmdline/... with optional peers for dsh-session-persistence/dsh-skill.
- **AWT application:** P1 guards packaging: every AWT guard plugin and both profile packages declare engines.dsh + peer pins to the attested rc; the §2.2 re-attestation workflow bumps these pins in one reviewed commit, making the compat window machine-checkable instead of prose.

#### Commit built artifacts and CI-assert zero drift, so git-source installs need no toolchain

- **Source:** 147228/dsh-black-whale .github/workflows/ci.yml; bugmaker2/dsh-plugin-template README; vlln/plugin-registry README (all cloned under .../scratchpad/eco/)
- **Pattern:** Ship `lib/` (built JS) in the repo and in `files:` so `dsh plugin add github:...` installs in seconds without running a build (pnpm blocks untrusted prepare scripts anyway); then make CI prove the committed artifacts match a fresh build with `git diff --exit-code -- lib` after `pnpm build`, plus `pnpm pack --dry-run` to inspect the exact release payload, on a 3-OS matrix.
- **Evidence:** ci.yml steps: `pnpm build` → 'Verify committed runtime artifacts: git diff --exit-code -- lib' → 'Inspect release package: pnpm pack --dry-run', matrix ubuntu/macos/windows. Template README: 'The generated lib/ directory is included in the package so direct Git installs can load the built JavaScript entry.' plugin-registry: '构建产物已入库（git 源安装不触发构建），一行命令直接装（实测约 15 秒）'.
- **AWT application:** P1/P3: commit AWT guard `lib/` output, add the drift check to CI, and pack-inspect releases — this is what makes `dsh plugin --profile awt-headless add github:...` work on an author machine with no TS toolchain, and it closes the 'broken documented global install' class of finding from the engineering review.

#### Scaffold-with-proof: the generator's --verify installs the fresh output into a throwaway DSH_HOME profile and asserts the mounted row

- **Source:** create-dsh-plugin@0.1.1 (npm) src/verify.js (unpacked at .../scratchpad/eco/npmpkgs/create-dsh-plugin-0.1.1/package/src/verify.js)
- **Pattern:** After scaffolding, run a 4-step proof: install → build → `npx @deepseek-ai/dsh plugin --profile verify add <target>` with DSH_HOME pointed at a mkdtemp dir → `--dump-config` and assert the plugin row is present; clean up the temp home; fail loudly with the stage name and last 2KB of output. The scaffold is not 'done' until it demonstrably loads into a real harness profile.
- **Evidence:** verify.js: `const dshHome = await mkdtemp(join(tmpdir(), 'dsh-verify-'))` … `run('npx', ['-y', '@deepseek-ai/dsh', 'plugin', '--profile', profile, 'add', targetAbs], { env: { ...env, DSH_HOME: dshHome } })` … `const found = r.stdout.includes(cfg.pluginId)` … '✔ VERIFY PASSED — the plugin compiles and loads into a real DSH profile'.
- **AWT application:** P2 `awt init`: end scaffolding with the same proof — boot `dsh --profile awt-headless --dump-config` against a temp DSH_HOME wired to the fresh workspace and assert every guard row and the 9 skills are mounted; a keyless, deterministic E0 gate that makes 'awt init succeeded' an executable claim.

#### Two-tier e2e: keyless registration-manifest verification separated from a paid live-model smoke

- **Source:** LaplaceYoung/oh-my-dsh e2e/run-e2e.sh + e2e/verify-e2e.mjs (clone: .../scratchpad/eco/oh-my-dsh/e2e/)
- **Pattern:** Tier 1 boots the real harness Loader with all plugins mounted from a local dsh source snapshot and asserts every plugin's expected registered surface against a checked-in EXPECTED map (plugin → exact tool/command names) — no LLM, no key, thousands of checks, runs anywhere. Tier 2 is a separate, small live-session smoke (`run-real-session.mjs`, real DeepSeek key, one real turn, 6 checks). Registration truth is cheap and exhaustive; model truth is expensive and minimal.
- **Evidence:** run-e2e.sh: '== 1/2 plugin registration ==' `node --import tsx ../verify-e2e.mjs "$(pwd)" examples/headless-agent/cordis.oh-my-dsh.yml` then '== 2/2 real LLM smoke =='. verify-e2e.mjs: `const EXPECTED = { '@oh-my-dsh/acp-sessions': { tools: ['acp_methods', …] }, … }` — 530 plugins / 2183 assertions, 'No LLM/agent needed — pure plugin-load verification.'
- **AWT application:** P1 gate structure: split AWT's CI into (a) a keyless mount-manifest test — profiles compose, guards register on the exact seams, skills discovered, denial codes exported — and (b) the §7 red-first typed-denial tests against a live headless run only where enforcement truth genuinely needs a live agent; keeps the loop fast and the E0 evidence class honest.

#### Compatibility claims are dated schema fields, and staleness is scanned but never auto-removed

- **Source:** dshworks/awesome-dsh-plugins README + data/plugins.json; awesome-dsh-plugin/awesome-dsh-plugin scripts/scan-decay.mjs (clones under .../scratchpad/eco/dshworks-registry/ and .../eco/awesome-dsh-plugin/)
- **Pattern:** Because the preview harness deletes mechanisms without migration (the `.dsh-plugin` manifest format was removed 2026-08-09, stranding every tutorial), a compatibility claim without a version and a date rots — so every registry entry carries `verifiedAgainst` (harness version) and `lastVerified` (date), and a scheduled decay scan flags gone/archived/dormant/unbundled entries into one tracking issue for a human, skipping anything inconclusive: 'a decay report must only ever contain evidence, not doubt.'
- **Evidence:** plugins.json entry: `"lastVerified": "2026-08-13", "verifiedAgainst": "0.1.0-rc.5", "status": "verified"`. scan-decay.mjs header: 'Flags — never removes… removal stays a human decision because… a scan can be wrong'. README: 'the `.dsh-plugin` manifest format was deleted on 2026-08-09 with no migration path'.
- **AWT application:** §2.2 scheduled re-attestation: emit `verifiedAgainst`+`lastVerified` into AWT's release notes and a machine-readable compat file; the scheduled workflow updates them or opens an evidence-only issue on failure — never silently edits claims. This is external precedent for AWT's dated-pinned-baseline posture and its evidence-class vocabulary.

#### Portable preset packages: versioned manifest, preview-then-confirm import, atomic validated install, never overwrite identifiers

- **Source:** dataelement/dsh-desktop docs/preset-packages.md (clone: .../scratchpad/eco/dsh-desktop/docs/preset-packages.md)
- **Pattern:** Shareable agent configuration travels as a ZIP (`.dshpreset`) with a manifest carrying `format`, `version`, and `sourceDshVersion`. Import is two-step (validate + preview, write only after confirmation); installation writes to a temp dir, validates through the harness's own preset scanner, then atomically moves into place; existing identifiers are never overwritten; the importer rejects absolute paths, parent traversal, and oversized archives; docs state plainly that 'custom presets are executable configuration' and warn on DSH version differences. Credentials and sessions are never packaged.
- **Evidence:** manifest example includes `"sourceDshVersion": "0.1.0-rc.6"`; 'DSH Desktop first validates and previews the archive, then writes it only after confirmation. Existing preset identifiers are never overwritten… Installation writes to a temporary directory, validates the resulting preset through the Harness preset scanner, and atomically moves it into the user preset root.'
- **AWT application:** P2 `awt init` and the §9 profile-family plan: treat the thesis-workspace scaffold and any shared `awt-*` profile as a preset package — manifest with sourceDshVersion, validate-before-write, atomic move, refuse to overwrite an existing workspace, exclude credentials/sessions — and reuse the same trust language for anything installable.

#### Exact-pin the harness closure; key any patch files to the exact pinned version; optionally vendor the whole closure and release in lockstep

- **Source:** dataelement/dsh-desktop package.json + patches/; salathleizhang/deepseek-harness-desktop README (clones .../eco/dsh-desktop/ and .../eco/dsh-desktop-tauri/); dsh-tui README for the dependency-level variant
- **Pattern:** Apps that must survive a preview harness pin every harness package to an exact version (no carets: `"@deepseek-ai/dsh": "0.1.0-rc.6"` across ~15 packages) and store pnpm patch files whose filenames embed that exact version (`@deepseek-ai+dsh-host-apiproxy+0.1.0-rc.6.patch`), so a harness upgrade physically forces patch review. The heavier variant vendors the entire `pnpm deploy` closure plus a portable Node runtime into the installer and shares the harness family's version/tag (`dsh-v*` triggers the desktop release) — lockstep releases. Either way, user data lives outside the install dir so upgrades never destroy it. dsh-tui applies the same idea one level down: pi-tui 'pinned at 0.80.7 with a pnpm patch… and bundled into lib/ so installs outside this repo never see an unpatched copy'.
- **Evidence:** dsh-desktop/package.json lines 44-57 all exact `0.1.0-rc.6`; patches/ dir listing with version-embedded filenames; tauri README: 'vendor/harness/ — the @deepseek-ai/dsh closure produced by pnpm deploy', 'Pushing a dsh-v* tag — the desktop app shares the dsh family's version and tag', 'upgrades leave user data untouched'.
- **AWT application:** §2.2/§12: AWT profiles should exact-pin `@deepseek-ai/dsh*` (not caret) with the attested baseline, and the P3 kill-gate fallback gains a concrete escape hatch — vendoring the deploy closure at the last-good rc keeps `awt` runnable even if upstream breaks, without forking. If AWT ever must patch a dependency, version-keyed patch files make the pin-review coupling mechanical.
